# 任务原型与组合指南

按任务家族选起点：先认原型（数据流形状），再认信任偏置（哪种错误更贵），规模真的难时才认规模模式。原型给的是不变式，不是模板——改编先例时删掉不属于不变式的域细节。

## 1. 原型地图

| 问题家族 | 起步形状 | 值得借的不变式 |
|---|---|---|
| 有界变更评审 | 差异分组 charter 扇出 → 独立反驳 | 不同评审 charter；只在能省验证时全场去重；独立反驳 |
| 未知 bug 总体 | 轮换视角狩猎 → 对 `seen` 去重 → 干轮收敛 → 多数怀疑 | 每轮换视角；对全部所见去重；连续干轮收敛；多数票怀疑 |
| 防御性安全评审 | 侦察 → 定向扇出 → 按严重度验证 | 侦察让后续视角变具体；严重度改变验证投入；条目独立 pipeline |
| 从粗糙输入提炼需求 | 独立提取视角 → 攻击歧义/范围/可行性的批判 | 多视角独立提取；未知项变成 `openQuestions` 返回 |
| 需求到技术设计 | 代码库落地先行 → 方案竞争 → 保真检查单独跑 | 设计前先接地；架构争议可交给决策原型；保真与设计分离 |
| 待办分解 | 多文档视角合并 → 反向批判查遗漏 | 多视角经判断合并；反向批判专查遗漏 |
| 能力排序 | 竞争策略暴露权衡 → 评审团选择 → 关键路径压测 | 选择之后还有一次对胜者的压力测试 |
| 开放设计决策 | 强制哲学多样 → 匿名评审团 → 嫁接合成 + 浮出异议 | 身份强制多样；匿名评审；合成时嫁接落选者优点 |
| 仓库上手/全景 | 勘察建不相交阅读域 → 合成（此屏障有辩护）→ 批判修复 | 勘察造不相交域；合成证明屏障合理；批判产出可执行修复 |
| 文档漂移审计 | 每文档独立 claims→checks pipeline | 无跨文档屏障——条目独立是默认而非特例 |
| API 迁移 | 发现 → 不相交分片 → 波次变更 → 全局一次验证 | 先发现后变更；分片不相交；波次全败即中止；全局验证只跑一次 |
| 依赖升级 | changelog 证据 join 本地用法 → 有界修复循环 | join 是真屏障；修复循环有界并暴露不稳定状态 |
| 行为保持重构 | 特征化安全网先行 → 每目标 net→change→保持检查 | 绿网是变更的门；每目标独立流水 |
| 死代码清除 | 多模态发现 → 默认保留的怀疑者 → 删除 opt-in 且顺序执行 | 独立发现模态 + 因删除代价不对称而默认保留；删除单线程 |
| 风险导向补测试 | 覆盖证据 + 爆炸半径判断 → 独立复核自验证写作者 | 证据与风险合成；自己验证过的要新鲜眼睛再查 |
| 不稳定测试诊断 | 廉价嫌疑扫查 → 实证复现 → 机制诊断 | 嫌疑与确认严格分离；诊断只看实证失败 |
| 发布就绪判断 | 就绪维度收证据 → 阻塞项被挑战 → 决策从结果结构推导 | 决策由形状推导，不由某个 agent 拍板 |
| 发布说明保真 | 读 diff 不信 message → claim→commit 与 commit→coverage 双向核查 | 双向核查：抓编造也抓遗漏 |
| 故障解释 | 无假设的证据收集 → 竞争解释 → 各配专职证伪者 | 收集者不得继承偏爱的故事；预测顶住攻击才存活 |
| 大反馈语料 | 校准词表 → 清单分片 → 代码聚合 → 头部主题深读 | 先校准后分片；聚合归代码；深读只给头部 |
| 研究问题 | 多模态线索 → 排序深读 → 带引用合成 → 批判轮 | 线索与深读分离；每条主张带引用；批判修复只跑一轮 |
| 端到端功能实现 | 会话层拆解段 → 不相交实现 → 评审段 | 段间结构化交接；不重审上段的验证 |

### 单阶段原型（可跨阶段串联）

五种最常见的单个工作流形状（对应 ultracode 的"一阶段一工作流"节奏）：

- **理解 Understand**：并行读者覆盖相关子系统 → 结构化地图（原型：全景/文档漂移）。
- **设计 Design**：N 个独立方案 → 评审团打分 → 嫁接合成（原型：开放设计决策）。
- **评审 Review**：维度 → 发现 → 对抗验证（原型：有界变更评审 + 未知总体的收敛纪律）。
- **调研 Research**：多模态线索 → 排序深读 → 带引用合成 → 批判（原型：研究问题）。
- **迁移 Migrate**：发现 → 不相交分片 → 波次变更 → 全局验证（原型：API 迁移）。

## 2. 模式嫁接

把两个原型的不变式拼起来时，写出拼接点：

- **未知尾巴的有界评审**：有界 diff 里可能藏着数量未知的微妙缺陷——借"未知总体"的收敛纪律（轮换视角 + `seen` 集）配"有界评审"的独立反驳；发现量大时按影响分档加权怀疑。轮次被上限停住时**不许**声称穷尽覆盖。
- **证据背书的转换**：多站点必须改且不许改行为——"API 迁移"的不相交分片 + "行为保持重构"的特征化门；门在每片变更**前**，全局构建/测试在全部变更**后**。分片重叠就放弃并发，改串行/漏斗。
- **语料到决策**：大语料要支撑一个产品选择——先"校准词表+清单分片+代码聚合"把证据坐实，再"竞争提案+匿名评审+嫁接合成"；保留引用让选中的设计能回溯到语料。
- **证据到解释**：go/no-go 取决于一个有争议的故障机制——"发布就绪"的带证据检查 + "故障解释"的证伪者；证据收集者不许继承被偏爱的故事。
- **先广后深**：先跑一遍广度原型找出需要关注的子集，只对最高风险子集跑深度对抗原型；未检查的余量显式返回。
- **人工检查点链**：产品判断无法诚实地自动化时，返回 `openQuestions` + `assumptions` + 建议的下次调用；后续会话用 `args` 供答案，工作流绝不模拟答案、也绝不等待它没有的交互原语。

## 3. 模式不相容性

- per-item pipeline 与全场评审可以共存，但评审在 pipeline 之后引入**真屏障**——为它辩护：什么需要完整字段？
- loop-until-dry 与静默 top-N **不相容**：隐藏上限毁掉干信号。截掉的条目必须留在返回的余量里。
- 默认反驳 vs 默认保留不是风格差异——按两个错误方向的代价不对称来选，并写进怀疑者提示词。
- 不相交共享树变更与（dsh 没有的）worktree 隔离解决不同问题：dsh 只有"构造性不相交"这一条路，分不出不相交就串行。
- 深于两段的组合走**会话层串联**（dsh 无嵌套钩子）——这与"一串小工作流"的 ultracode 节奏天然一致。
- 一次性生成的抽象会加重审查负担：优先内联，重复真实出现再抽。

## 4. 多阶段串联模板

ultracode 的典型节奏（每段一个工作流，段间你读结果再决定）：

```
段1 理解  → 结构化地图、openQuestions
段2 设计  → 方案 + 评审团裁决 + 异议
（读裁决；若有 openQuestions → 会话层问用户，答案进下一段 args）
段3 实现  → 不相交分片变更 + 特征化验证报告
段4 评审  → 维度发现 → 对抗确认的缺陷清单
```

串联纪律：

1. 每段脚本**小而边界清晰**；上一段的输出经 `args` 或结构化返回值流向下一段。
2. 段间做判断：读结构化结果，砍掉不值一段的残余工作（琐碎的直接在主对话做）。
3. 段失败/返回空 → 停下来诊断，不要假装成功继续。
4. 每段的 meta.phases 与段内 `phase()` 对齐——进度树按段呈现，用户能看懂现在到了哪一步。
5. 呈现：段开始时 `log()` 一句"第 N/M 段：<做什么>"，段结束 `log()` 关键结论一行。

## 5. 改编先例时的提问清单

1. 这个阶段是因为先例的**领域**存在，还是因为它的**编排不变式**存在？
2. 新任务能提供下游阶段期望的同等证据与结构化边界吗？
3. 先例的不确定性偏置与这里的危害模型匹配吗（默认反驳还是默认保留）？
4. 先例的屏障在新数据流下逻辑上必要吗？
5. 什么条件证明**覆盖/收敛**，什么条件只是**停止花钱**？
6. 任何一个 agent 返回 `null` 时，什么还成立？
7. 哪个上限、被省略的分片、有争议的结果、开放问题必须出现在最终对象里？
